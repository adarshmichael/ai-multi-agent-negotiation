## 📋 Executive Overview

**NegoSim** simulates dynamic, multi-round negotiations between autonomous AI agents, or between a human user and AI agents. It evaluates structured offers against hard numeric constraints, tracks concession dynamics across every round, detects negotiation deadlocks, and generates analytical outcome reports — all delivered in real-time via WebSockets.

- **Problem**: Negotiating effectively requires deliberate practice, but coordinating roleplay with domain experts is costly and logistically difficult.
- **Solution**: A full-stack platform where LLM-powered agents (driven by Google Gemini) represent stakeholders with explicit roles, numeric hard constraints, configurable goals, and distinct negotiation personalities. Both fully autonomous simulations and interactive human-vs-AI practice sessions are supported.
- **Key Capabilities**:
  - **Simulation Mode**: Two AI agents negotiate autonomously until agreement, deadlock, or max rounds.
  - **Practice Mode**: A human participant takes the role of one agent in a live, turn-by-turn session against the AI.
  - **LLM Mode**: Decisions are generated by Google Gemini using full context-aware prompts.
  - **Rule-Based (Mock) Mode**: A deterministic personality-parameterized engine generates decisions instantly without any API calls — fully functional offline.
- **Target Users**: Students learning negotiation theory, professionals training for high-stakes deals, and researchers studying AI-driven game theory.
- **Key Technologies**: Vanilla JS/CSS3 (Frontend), Node.js/Express (Backend), WebSocket (`ws`) for real-time events, `@google/generative-ai` for LLM reasoning, MongoDB/Mongoose for user authentication and persistence.

## 🎯 Project Objectives

1. Provide a realistic, low-stakes environment for humans to practice negotiation against contextually intelligent AI agents.
2. Demonstrate autonomous AI-to-AI negotiation with personality-driven concession strategies and hard constraint enforcement.
3. Build a robust 5-module decision engine pipeline: **Offer Evaluation → Agent Decision → Counteroffer Generation → Concession Tracking → LLM Prompt Integration**.
4. Ensure strict adherence to numeric hard constraints (e.g., maximum budget, minimum acceptable price) at both the LLM prompt layer and the backend guardrail layer.
5. Deliver fully real-time UI updates using WebSockets without the overhead of a heavy frontend framework or build system.
6. Produce structured, exportable negotiation outcome reports with per-agent satisfaction scores, concession timelines, and key insights.
7. Provide a graceful multi-level fallback chain: **LLM (Gemini) → Mock Generator → Rule-Based Engine** to guarantee the negotiation always progresses.

## ✨ Key Features

### 1. Five-Module Decision Engine Pipeline

The backend implements a sequential five-module decision pipeline per agent turn:

| Module | Service | Purpose |
|---|---|---|
| **M1: Offer Evaluation** | `offerEvaluation.service.js` | Deterministically evaluates the opponent's offer — `FAVORABLE`, `PARTIALLY_ACCEPTABLE`, or `UNACCEPTABLE` — relative to the agent's target, constraints, and round urgency. |
| **M2: Decision Selection** | `decisionProvider.js` | Selects `ACCEPT`, `COUNTER`, or `REJECT` using either Gemini LLM or the rule-based engine, with constraint enforcement as a final override layer. |
| **M3: Counteroffer Generation** | `counteroffer.service.js` | Generates a deterministic, personality-aware counteroffer using a Boulware-style target-anchored concession strategy, rounded to the nearest ₹500. |
| **M4: Concession Tracking** | `concession.service.js` | Records every offer movement, validates against safeguard rules (`REVERSAL`, `EXCESSIVE`, `STAGNATION`, `LIMIT_BREACH`), and computes full concession snapshots. |
| **M5: LLM Prompt Integration** | `promptBuilder.js` | Embeds the M1–M4 structured context (evaluation result, deterministic decision, counteroffer parameters, concession state) directly into the Gemini prompt so LLM output is consistent with deterministic logic. |

### 2. Personality-Parameterized Negotiation

Seven distinct negotiation personalities are configured in `backend/config/personalityParams.js`, each with unique initial offer factors, concession rates, acceptance thresholds, and per-round movement caps:

| Personality | Initial Anchor | Concession Rate | Max Move/Round |
|---|---|---|---|
| Aggressive | 58%/142% of limit | 6% | 8% |
| Competitive | 60%/140% | 7% | 8% |
| Risk-Averse | 67%/133% | 10% | 12% |
| Analytical | 65%/135% | 9% | 10% |
| Professional | 68%/132% | 11% | 12% |
| Collaborative | 72%/128% | 14% | 18% |
| Flexible | 70%/130% | 16% | 22% |

### 3. Real-Time WebSocket Arena

- A `WebSocketServer` (`ws`) shares the same HTTP port via `server.on('upgrade', ...)`.
- The `NegotiationEngine` broadcasts per-event payloads after every action.
- Clients reconnect-safe: on reconnection, `connection_established` sends the full current session state.
- Multiple concurrent WebSocket clients per session are supported via a `Set`-based registry.

### 4. Agreement & Deadlock Intelligence

- **Auto-Agreement**: Offers within 1% tolerance of each other trigger automatic deal closure without requiring an explicit `accept` decision.
- **Deadlock Warning** (non-terminating): Emitted as an in-chat banner when all agents have been stagnant for N-1 rounds.
- **Hard Deadlock**: Terminates with `REJECTION` result when all agents have been stagnant for N consecutive rounds (default: 4).
- **Single-agent stagnation** only triggers a warning — it never terminates the session, preventing premature endings from slow-conceding aggressive personalities.

### 5. Structured Outcome Reporting

`report.service.js` produces a full report object including:
- **Satisfaction Scores** (0–100): Constraint-aware scoring for each agent based on the final agreed price relative to their target and hard limit.
- **Concession Timeline**: Round-by-round entry grouped by round number with action type and formatted offer amounts.
- **Decision Breakdown**: Per-agent count of `accept`, `counter_offer`, and `reject` decisions.
- **Key Insights**: Automatically generated textual insights (largest conceder, efficiency, constraint respect, satisfaction summary).

## 🎛️ Modes of Operation

NegoSim operates across two independent dimensions:

```
Participant Dimension:  Simulation Mode (AI ↔ AI)  |  Practice Mode (Human ↔ AI)
Engine Dimension:       Gemini LLM Mode             |  Rule-Based (Mock) Mode
```

| Mode | Description |
|---|---|
| **Simulation (AI vs AI)** | Both parties controlled by the autonomous engine. Runs to completion without human intervention. |
| **Practice (Human vs AI)** | Human takes the first agent role. The engine pauses on human turns, emits `human_turn_required`, and awaits WebSocket `human_input`. |
| **Gemini LLM Mode** | Contextual decisions by Google Gemini. Requires `GEMINI_API_KEY`. Falls back to Mock if keys are unavailable. |
| **Rule-Based Mode** | Fully deterministic, personality-parameterized decisions. No API key required. Runs instantly. |

### Data Flow

1. **Setup (UI)**: User selects scenario, configures agent goals/constraints/personalities in the wizard → stored in `AppState`.
2. **Session Creation**: `ApiService.createNegotiation()` → `POST /api/negotiations` → `negotiation.controller` validates payload → `negotiation.service` creates in-memory session → returns `negotiationId`.
3. **Connect & Start**: Frontend opens WebSocket (`ws://host?negotiationId=...`) → calls `POST /api/negotiations/:id/start` → engine begins autonomous loop.
4. **Turn Execution (per round)**:
   - Engine detects agent type (`human` vs AI).
   - **AI Turn**: M1 evaluates opponent offer → M2 selects decision via LLM or rule engine → M3 generates counteroffer → M4 validates and records concession → M5 prompt is enriched with M1–M4 context for LLM calls.
   - **Human Turn**: Engine broadcasts `human_turn_required` → frontend mounts `HumanInput` panel → human submits via WS → engine resumes.
5. **Broadcast**: Engine broadcasts `agent_message`, `offer_updated`, `round_started`, `agent_thinking`, `deadlock_warning` events over WebSocket.
6. **UI Update**: `ApiService` receives events → dispatches to `LiveNegotiationScreen` → updates `ConversationLog`, `StatePanel`, `NegotiationTimeline`, `OrchestratorIndicator`, agent cards.
7. **Completion**: Agreement or termination condition detected → engine broadcasts `negotiation_completed` with full summary and concession data → UI renders terminal result card.

## ⚙️ Decision & Concession Engine Architecture

### Role-Aware Concession Metrics

The `concession.service.js` (Module 4) tracks and validates every offer movement:

| Metric | Formula / Description |
|---|---|
| **Step Concession Amount** | `\|current_offer - previous_offer\|` |
| **Step Concession %** | `(concession_amount / \|previous_offer\|) × 100` |
| **Total Concession** | Sum of all step concession amounts from initial position |
| **Remaining Flexibility** | Distance from current offer to agent's hard constraint limit |
| **Flexibility Consumed %** | `(1 - remaining_flexibility / initial_flexibility) × 100` |
| **ZOPA** | `max_buyer_limit - min_seller_limit` (computed per scenario) |

### Concession Safeguard Flags

`validateConcession()` enforces four safeguard rules before any offer is finalized:

| Flag | Trigger | Effect |
|---|---|---|
| `LIMIT_BREACH` | Proposed offer violates hard constraint | Clamped to limit |
| `REVERSAL` | Agent moves in wrong direction (e.g. buyer going lower, seller going higher) | Position frozen at previous offer (±₹500 tolerance) |
| `EXCESSIVE` | Single-round move exceeds personality's `maxSingleRoundPct` | Offer capped to personality limit |
| `STAGNATION` | Less than ₹500 movement in last 3 consecutive rounds | Warning flag raised |

### Counteroffer Strategy (Module 3)

Boulware-style target-anchored gradual concession:

```
Buyer  (moves UP):  raw = myLastOffer + (opponentOffer - myLastOffer) × effectiveRate
Seller (moves DOWN): raw = myLastOffer - (myLastOffer - opponentOffer) × effectiveRate

effectiveRate = concessionRate × (1 + urgencyFactor × 2.5)
urgencyFactor = currentRound / maxRounds  (increases pressure near end)
```

All offers are rounded to the nearest ₹500 and clamped to hard constraint limits.

Three fully configurable scenarios are built into the platform. Each agent supports user-overridable goals, constraint selections, and numeric boundaries.

| Scenario | Role 1 (Buyer/Minimizer) | Role 2 (Seller/Maximizer) | Default ZOPA |

| **Job Offer Negotiation** | Candidate — Min CTC: ₹12,00,000 | Employer — Max CTC: ₹18,00,000 | ₹6,00,000 |
| **Project Budget Allocation** | Project Manager — Min Budget: ₹20,00,000 | Finance Manager — Max Budget: ₹30,00,000 | ₹10,00,000 |

### Vendor Pricing Negotiation — Example Exchange

```mermaid
sequenceDiagram
    participant V as Vendor (Seller)
```

## 💻 Local Development Setup

### Prerequisites

- **Node.js** >= 18.0.0
- **MongoDB** (optional, for authentication features) — local or [MongoDB Atlas](https://cloud.mongodb.com)
- **Google Gemini API Key** (optional) — get one at [Google AI Studio](https://aistudio.google.com)

### 1. Backend Setup

```bash
# Navigate to backend
cd backend

# Install dependencies
npm install

# Configure environment
cp .env.example .env
# Edit .env — add your GEMINI_API_KEY and MONGODB_URI

# Start (development with file-watching auto-restart)
npm run dev

# OR start (production)
npm start
```

The backend starts on:
- **HTTP API**: `http://localhost:8001/api`
- **WebSocket**: `ws://localhost:8001`
- **Interactive Health Check**: `http://localhost:8001/api/health`

### 2. Frontend Setup

The frontend is pure static HTML/CSS/JS — no build step required.

```bash
# From the repository root, serve with Python
python3 -m http.server 8000

# OR use any static server
npx serve .
```

Open **`http://localhost:8000`** in your browser.

> **Local vs. Deployed Backend**: `js/data/api.js` defaults to the deployed Render backend URL. To use your local backend, update `BASE_URL` and `WS_URL` in `js/data/api.js` to `http://localhost:8001/api` and `ws://localhost:8001`.

## ⚠️ Known Limitations & Future Scope

| Limitation | Detail | Planned Resolution |
|---|---|---|
| **In-Memory Session Storage** | Active negotiations live in a `Map` in `negotiation.service.js`. Restarting the backend resets all sessions. | Migration to MongoDB or PostgreSQL (service layer already abstracted for clean swap). |
| **LLM Rate Limits** | Free-tier Gemini API keys hit quota limits under heavy concurrent load. | Multi-key rotation is implemented; configurable via `GEMINI_API_KEYS`. The mock fallback ensures continuity. |
| **Frontend Auth Integration** | Auth REST routes are fully functional. Frontend `app.html` has a login screen but the wizard (`index.html`) does not yet gate access behind authentication. | Full auth-gating of the wizard UI in a future milestone. |
| **AI Typing Indicators** | No real-time streaming of LLM token generation; the `agent_thinking` event serves as a placeholder. | Implement Gemini streaming API for live token streaming. |
| **Advanced Deadlock Recovery** | The engine currently terminates on hard deadlock. | Allow AI to propose alternative deal packages before final breakdown. |
| **Post-Negotiation Coaching** | No scoring or AI feedback for human negotiators in Practice Mode. | Planned coaching analytics module using the outcome report data. |
| **Mobile UI** | Basic responsive breakpoints exist in `css/responsive.css` but the 3-column arena layout degrades on narrow screens. | Full mobile-first arena redesign planned. |
